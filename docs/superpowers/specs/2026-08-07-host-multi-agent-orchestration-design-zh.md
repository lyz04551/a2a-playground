# Host 多智能体编排设计

## 1. 背景

当前 Host Agent 的主要行为类似智能路由器：选择一个智能体、调用 `send_task`，再总结该智能体的响应。现有 Run、Task 和 Event 模型已经能够记录多次委派，但 Host 尚不具备显式计划、依赖图、结果评估以及可靠的重试和重新规划能力。

本设计将 Host 从单智能体路由器升级为受控的多智能体编排器，同时保留简单请求的快速执行路径。

## 2. 目标

- 自动判断请求需要一个还是多个智能体。
- 将复杂请求拆分成可审计的子任务。
- 独立子任务支持并行执行，存在前后依赖的子任务支持串行执行。
- 只向后续智能体传递完成其任务所需的前序结果。
- 在回复用户前，评估已有结果是否完整满足请求。
- 瞬时故障自动重试一次；重试失败后，在可能的情况下改用其他合适的智能体。
- 保留有价值的部分结果，并如实说明未解决的部分。
- 所有写操作继续受现有审批流程控制。
- 让 LangGraph 和 ADK Host 遵循相同的编排语义。
- 通过 Run 事件展示规划、委派、重试、重新规划、审批和综合过程。

## 3. 非目标

- 允许已注册智能体自由地相互调用。
- 构建不受限制的递归智能体网络。
- 因为另一个智能体建议执行变更，就自动绕过审批。
- 在本轮优化中引入分布式工作流引擎或跨进程持久化任务队列。
- 替换现有 A2A Gateway、持久化层或前端 Run 模型。

## 4. 选定架构

采用混合架构：大语言模型负责语义规划和结果评估，确定性的后端代码负责验证和执行计划。

编排生命周期包括：

1. **分析（Analyze）**：判断任务范围、风险，以及单智能体快速路径是否足够。
2. **规划（Plan）**：生成包含子任务及其依赖关系的结构化计划。
3. **调度（Schedule）**：验证计划并执行就绪的子任务，在安全的情况下并行运行。
4. **评估（Evaluate）**：判断结果是否满足用户目标和各子任务的完成标准。
5. **综合（Synthesize）**：生成统一、连贯的用户回复，说明完成内容、证据和未解决事项。

Host 是唯一协调者。已注册智能体只接收边界清晰的任务提示，不获得直接调用其他智能体的能力。

## 5. 核心组件

### 5.1 能力注册表

智能体注册信息统一规范为能力档案。每份档案包含：

- 稳定的智能体 ID 和显示名称；
- 描述和 Agent Card 地址；
- 技能 ID、描述、标签和示例；
- 支持的输入和输出模式；
- 风险等级以及是否只读；
- 操作限制和不适用场景；
- 健康状态和可用性；
- 可选优先级，仅用于确定性地打破候选者平局。

注册表基于能力而不是名称进行匹配。候选智能体排序综合考虑技能匹配度、风险兼容性、健康状态和已声明限制。离线智能体不会进入候选列表。

三个内置智能体保持明确分工：

- `k8s-ops`：只读诊断，包括日志、事件、健康状态和资源检查；
- `k8s-security`：只读安全评估，包括 RBAC、网络、镜像和策略；
- `k8s-orchestrator`：变更规划和经过审批的写操作。

### 5.2 结构化计划

规划器返回经过验证的对象，其逻辑结构如下：

```json
{
  "summary": "预期目标的简短说明",
  "tasks": [
    {
      "id": "diagnose",
      "agent_id": "k8s-ops",
      "objective": "确定发布失败的原因",
      "input": "用户请求及相关已知上下文",
      "depends_on": [],
      "completion_criteria": ["根因有可观察证据支持"],
      "risk": "read",
      "max_attempts": 2
    }
  ]
}
```

计划验证会拒绝未知智能体、重复任务 ID、循环依赖、缺失依赖、不兼容能力，以及将写操作分配给只读智能体等情况。为防止失控拆分，计划规模设有上限：初始限制为最多六个子任务，每个子任务最多执行两次，其中包括首次执行。

简单请求在内部仍会生成单节点计划。前端可以将其展示为一次直接委派，避免引入不必要的视觉噪音。

### 5.3 调度器

调度器根据依赖图计算就绪任务：

- 没有未完成依赖的任务可以并行运行；
- 依赖任务只有在所有必要前置任务完成后才启动；
- 依赖任务会收到从前序结果中提炼出的紧凑且带来源标识的上下文；
- 任何子任务都不能自行创建新任务；
- 存在写入风险的任务必须停在审批环节，并通过现有审批机制恢复。

并发数量受配置限制，初始值为三个。调度器负责管理任务状态流转和取消传播。

### 5.4 上下文构建器

上下文构建器使用以下信息生成每个智能体的任务提示：

- 子任务目标和完成标准；
- 原始用户请求中与该任务相关的部分；
- 按来源任务和智能体标记的前序结论；
- 适用约束，包括只读要求和审批要求；
- 明确的响应契约，要求返回结论、证据、不确定性和建议的后续步骤。

系统不会向智能体转发原始对话全量历史或无关的其他智能体输出。较大的前序输出会被压缩总结，同时保留对来源任务的引用，以便追踪。

### 5.5 结果评估器与重新规划器

每个结果均按照对应任务的完成标准评估。评估结果包括：

- `sufficient`：结果充分，任务完成；
- `insufficient`：结果不足；如果仍有尝试次数，则补充更明确的上下文后重试；
- `failed`：执行失败；瞬时故障允许重试一次；
- `blocked`：需要审批或用户补充输入。

第二次尝试仍未成功时，Host 会查找另一个能力兼容的智能体。如果存在替代智能体，则替换失败的计划节点并记录重新规划事件。如果没有替代者，则阻塞无法继续的依赖任务，保留已经完成的独立结果，并在最终回复中说明部分完成情况。

重新规划不能把只读任务变成写任务、扩大用户请求范围，也不能绕过审批。

### 5.6 结果综合器

结果综合器接收计划和规范化后的任务结果，而不是未经整理的完整执行记录。最终回复必须：

- 直接回答原始请求；
- 协调相互冲突的结论，或明确指出冲突；
- 区分已观察事实与建议；
- 在有帮助时说明参与协作的智能体；
- 报告失败或阻塞的部分；
- 在没有执行证据时，绝不声称审批操作已经执行。

各智能体的响应属于中间产物，不能原样作为 Host 的最终回复。

## 6. 统一 Host 接口

LangGraph 和 ADK 集成共同使用一套编排服务，不再分别维护不同的规划提示和工具语义。

统一接口提供：

- 列出智能体能力并进行候选排序；
- 创建和验证计划；
- 通过 A2A Gateway 执行一个边界明确的子任务；
- 评估并规范化结果；
- 综合最终回复。

各框架的 Manager 只负责把模型和工具事件转换为统一的 Host 事件流。所有位置统一使用稳定的智能体 ID；ADK 当前按显示名称路由的方式将迁移到稳定 ID。

现有 `send_task` 工具继续作为底层委派原语保留，但不再承担完整的编排策略。

## 7. Run、Task 与 Event 模型

现有根任务表示 Host 编排过程，每个计划节点对应一个子任务。重试属于同一个子任务的不同尝试，而不是新的逻辑任务；改用其他智能体时，会在任务元数据和重新规划事件中记录。

新增或统一以下事件：

- Host 计划已创建并通过验证；
- 子任务就绪、已委派、已开始、已完成、失败或阻塞；
- 依赖上下文已准备；
- 已安排重试；
- 计划已修订并替换智能体；
- 需要审批以及审批后恢复；
- 结果评估完成；
- 最终综合开始和完成。

每个事件都包含 Run ID、逻辑任务 ID、父任务 ID、适用时的智能体 ID、序列号以及安全的元数据。敏感工具输出不会被复制到事件元数据中。

事件适配器继续兼容现有的 `HOST_PLANNING`、`TASK_DELEGATED`、工具、消息、审批和终止事件。新增事件用于增强执行轨迹，不改变 Direct 模式。

## 8. 失败、取消与审批

- 智能体或 Gateway 的瞬时故障重试一次。
- 结果不充分时，补充更明确的提示后重试一次。
- 尝试次数耗尽后，Host 尝试选择一个能力兼容的替代智能体。
- 一个独立分支失败时，不取消其他已经成功或仍可执行的分支。
- 必要前序任务失败时，只阻塞依赖它的后续任务。
- 用户取消任务后，在底层支持的情况下停止活跃子任务，并且不再启动新任务。
- 等待审批时暂停受影响的写任务及其依赖后续任务；无关的只读分支可以继续完成。
- 审批被拒绝时生成有效的部分结果，不能伪造为执行故障。
- 只有当最终综合如实反映所有任务的终态时，Run 才标记为 `completed`。如果根编排本身失败，导致无法产生有意义的回复，则标记为 `failed`。等待用户审批期间保持 `approval_required`。

## 9. 前端行为

多智能体执行轨迹展示：

- 以小型依赖图或有序任务列表展示 Host 计划；
- 并行分支和依赖关系；
- 每个任务选择的智能体以及选择原因；
- 当前尝试次数、重试和智能体替换；
- 审批暂停状态；
- 每个任务的状态和简短结果摘要；
- 作为主要对话回复的最终综合结果。

简单的单智能体请求继续使用当前紧凑展示。界面不暴露隐藏提示词原文或敏感工具参数。

## 10. 兼容与迁移

- Direct 模式保持不变，继续只调用用户明确选择的一个智能体。
- Auto 模式采用结构化编排。
- 旧的智能体注册记录在缺少新增能力字段时使用保守默认值进行规范化。
- 扩展现有智能体 YAML 文件，但不使已有字段失效。
- 旧的 Run 历史仍然可以读取；新增字段和事件类型均为增量扩展。
- 首先在 LangGraph Host 中接入统一服务，然后让 ADK 使用同一服务和稳定 ID 契约。

## 11. 测试策略

每项行为均采用测试驱动开发。必须覆盖：

- 简单请求采用单智能体快速路径；
- 复杂请求生成有效的多节点计划；
- 独立任务在并发限制内并行执行；
- 依赖任务等待前序完成，并且只接收相关前序上下文；
- 无效、循环、超大或能力不兼容的计划被拒绝；
- 瞬时故障只重试一次；
- 结果不足时触发经过优化的重试；
- 尝试耗尽时改用兼容的智能体；
- 没有替代智能体时生成如实的部分结果；
- 写操作不能分配给只读智能体；
- 审批暂停并恢复正确的任务及依赖链；
- 取消后不再调度后续任务；
- 智能体结论冲突时，最终综合明确呈现冲突；
- LangGraph 和 ADK 适配器产生等价的规范化事件；
- 旧智能体注册信息和旧 Run 历史保持兼容；
- 前端状态能够渲染单任务、并行、串行、重试、重新规划、审批和部分失败轨迹。

## 12. 实施顺序

1. 通过单元测试定义计划、能力、结果和事件契约。
2. 扩展智能体注册元数据和内置智能体 YAML 文件。
3. 实现计划验证、依赖调度、并发限制和上下文构建。
4. 增加结果评估、重试、替换和部分结果语义。
5. 将 LangGraph Host 接入统一编排服务。
6. 更新 Run 持久化和事件规范化。
7. 更新前端编排轨迹。
8. 将 ADK Host 迁移至统一服务和稳定智能体 ID。
9. 运行后端、运行时、Agent Card、前端状态和冒烟回归测试。

## 13. 验收标准

满足以下条件时，本轮优化视为通过验收：

- 简单诊断请求只委派一次，并返回经过综合的答案；
- 同时需要诊断和安全审查的请求，会并行调用两个只读智能体；
- 先诊断后修复的请求，会把诊断结论传递给修复计划，并在写操作前等待审批；
- 智能体失败后执行一次重试，随后安全地改用替代智能体，或明确返回部分结果；
- 界面和持久化事件流能够展示每个智能体被调用的原因以及结果组合方式；
- 任何路径都不能执行未经审批的写操作；
- 两种 Host 框架适配器遵守相同的稳定 ID 和编排契约；
- 所有相关自动化测试和构建均通过。
