# 审批写操作生命周期设计

## 问题

用户请求“可以创建一个nginx pod么 然后检查一下有没有什么问题”时，Auto 工作流可能在 Kubernetes 写操作真正生效前，就把审批任务标记成完成。重复审批路径会返回“审批已处理，未重复执行。”，该文本又被错误地当成写操作成功结果。Host 随后进入验证阶段，发现资源不存在，并在后续轮次用不同任务 ID 创建逻辑上相同的任务，直到耗尽运行预算。

同一次运行还暴露了 MCP session 的并发安全问题。多个读取工具并行复用同一 session 后，出现 `Attempted to exit cancel scope in a different task than it was entered in` 和 45 秒超时；但使用全新 client 直接调用同一个 `apply_k8s_yaml` 只耗时 0.238 秒。

## 目标

- 审批决定被快速确认，HTTP 响应不等待远端写操作完成。
- 只有完全一致的 MCP 调用真实成功返回后，审批写任务才能成为成功状态。
- 重复审批最多执行一次写操作，且不得制造虚假成功结果。
- 每个已持久化的 `tool.called` 最终恰好对应一个终态 `tool.completed`。
- 一个可复用 MCP session 不得被多个任务并发使用，异常 session 必须销毁。
- Auto Host 只能在写操作确认成功后进入验证阶段。
- 逻辑等价的失败任务不能通过更换任务 ID 绕过跨轮重试限制。
- 使用原始中文请求对审批、写操作、验证和最终收口进行确定性的回归验证。

## 非目标

- 不改变公开的审批参数结构或 action digest。
- 不在本次修复中用持久化任务队列重写整个编排系统。
- 不改变 Kubernetes 策略或 `apply_k8s_yaml` 的业务语义。

## 设计

### MCP session 安全

`K8sMCPClient` 使用一个操作锁串行化 connect、call 和 disconnect 的状态转换。LangGraph 仍可并行调度工具节点，但共享同一个 client/session 的调用必须逐个执行。出现超时、传输异常或 cancel-scope/session 异常时，先废弃并断开当前 session，后续调用再建立新连接。只有明确的传输失败允许现有的一次重连；写操作收到不明确响应时不得盲目重试。

### 审批执行所有权

审批持久化需要区分“决定已接受”和“执行已终结”。第一个请求以原子方式取得执行所有权。对于 Auto 运行，接口立即返回“已接受”，并在受跟踪的后台任务中执行该 continuation。重复请求不能再次调用 Agent，也不能把“审批已处理，未重复执行。”作为执行证据传给 `resume_after_approval`；它只返回当前审批状态，由原始执行者负责发布最终结果。

前端在审批决定被接受后结束按钮 loading，后续执行中、成功或失败状态均由运行事件流更新。

### 事件与任务闭环

continuation 返回后，`resume_after_approval` 持久化唯一的 `approval.decided`，用唯一的 `tool.completed` 关闭匹配的未完成工具调用，并将暂停任务标记为 completed、failed 或 blocked。只有包含真实执行结果的成功 continuation 才能进入 Host checkpoint 的 successful 集合。空结果、重复请求结果、Agent 不可用、超时或失败结果不得启动验证阶段。

### 跨轮循环保护

Host 状态记录不依赖模型生成任务 ID 的语义 fingerprint。fingerprint 覆盖 workflow role、目标 Agent、归一化后的 objective/input，以及可获取的写操作身份。逻辑上等价的失败写任务在不同轮次共享同一个重试预算。预算耗尽后，Host 直接发出带累计失败原因的终态失败，不再要求模型生成另一个等价任务。

真正的新任务仍沿用现有的单任务重试行为。

## 失败处理

- MCP 成功：关闭写工具调用、标记任务成功并恢复 Host 验证。
- MCP 明确错误或超时：用错误关闭工具调用并结束运行，不验证未经确认的副作用。
- 执行期间重复审批：返回已接受/当前状态，不执行第二次写操作，不发布合成成功。
- 审批后的 Agent stream 失败：关闭工具调用并使用传输错误终止运行。
- Host 重复生成等价任务：跨轮预算耗尽后拒绝该任务并结束运行。

## 测试

1. Runtime MCP 测试：针对同一 fake session 并发调用，断言实际串行；针对超时/session 异常，断言 session 会失效。
2. 审批 service/API 测试：并发提交重复审批，断言只执行一次 Agent continuation，且接口快速返回已接受。
3. Run service 测试：断言只有具体执行成功才能恢复验证，且每个未完成写工具调用只关闭一次。
4. Host engine 测试：断言跨轮、跨任务 ID 的等价失败任务不能突破语义重试限制。
5. 前端测试：断言接口接受审批后按钮结束 loading，后续状态来自运行事件。
6. 验收测试：使用完整原始请求“可以创建一个nginx pod么 然后检查一下有没有什么问题”，在审批点暂停，以确认成功的 apply 结果恢复，验证 Pod，并在没有重复写操作或孤立工具调用的情况下进入唯一终态。
7. 真实 MCP smoke：使用唯一 Pod 名称，记录耗时、验证资源存在及 Ready，并在测试后清理资源。

## 验收标准

- 审批按钮不会在 MCP 执行期间持续 loading。
- 写操作结束后不存在残留的 `Working` 工具。
- 第 N+1 轮不能在第 N 轮审批写操作得到终态执行结果前启动。
- 原始请求必须完成“预检 → 一次审批写入 → 验证 → 最终回答”，或者只失败一次并给出精确原因。
- 后续轮次不得出现等价的重复创建循环。
